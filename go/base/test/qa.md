# QA

## 如何理解 comparable

- comparable 是 排除了 slice map func 后的 any。 map 的key 必须是 可比较（==、 !=）的

### 为什么 slice 不是 comparable

- 核心原因是 Go 语言设计时为了避免歧义、性能问题和逻辑混乱
- slice 的本质是 “引用类型”，但比较语义不明确
slice 的底层结构包含三个部分：ptr（指向底层数组的指针）、len（长度）、cap（容量）。如果允许 == 比较，存在两种可能的语义：

比较 “引用是否相同”（即是否指向同一个底层数组的同一区间）；
比较 “内容是否相同”（即所有元素是否一一相等）。

这两种语义在实际开发中都可能被需要，但 Go 语言不希望隐式选择其中一种（可能导致开发者误解）。例如：
如果 a == b 按 “引用” 比较，结果为 false；按 “内容” 比较，结果为 true。这种歧义会导致逻辑错误。

``` go
a := []int{1, 2}
b := a[0:2]  // 与 a 共享底层数组，引用不同但内容相同
```

- 内容比较的性能成本过高

- 特殊情况（nil 切片与空切片）的逻辑混乱，与之相反的 JS 选择了一堆默认值，从而导致各种类型比较的混乱。

### 为什么 map 不是 comparable

- map 的本质是 “引用类型”，但比较语义存在歧义
  - 比较引用是否相同：即两个 map 变量是否指向同一个底层哈希表（类似指针比较）；
  - 比较内容是否相同：即两个 map 中的所有键值对是否一一对应相等。

``` go
m1 := map[int]int{1: 2}
m2 := m1  // m2 与 m1 指向同一个底层 map
m3 := map[int]int{1: 2}  // m3 与 m1 内容相同但引用不同
```

### 为什么 func 不是 comparable

- 函数的 “值” 无法被明确定义

``` go
f1 := func() {}
f2 := func() {}
// f1 == f2 应该返回 true 还是 false？
// 逻辑相同但内存地址不同，比较结果无意义
```

- 闭包的比较会导致逻辑混乱

``` go
x := 1
f1 := func() int { return x }
x = 2
f2 := func() int { return x }
// f1 和 f2 代码相同，但捕获的 x 值不同，行为不同
// 此时 f1 == f2 若返回 true 会误导开发者
```

### channel 和 指针为什么可比较？比较的是什么？

- channel 是引用类型，比较的是指针是否相同，是否指向同一个底层通道实例（即是否为 “同一个通道”）。
- 指针是值类型，比较的是值是否相同，是否指向同一块内存地址（即是否指向同一个变量实例）。

### 如何理解 channel 不存在内部状态的隐式修改？往通道里增加了 内容，不会有影响吗

- 这里的 “内部状态的隐式修改” 并非指 channel 的缓冲区内容，而是指 channel 作为一个对象的核心标识不会被修改。
- Map 的内容修改会导致内部结构变化
- Slice 的长度和容量变化可能影响语义

## var x interface{} = 10, 如何理解 interface

- interface{} 和 any 本质上是完全等价的，它们都表示任意类型。any 是 Go 1.18 引入的泛型特性中的一个语法糖，用于简化 interface{} 的写法
