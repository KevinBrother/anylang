# 深入理解 GO 并发编程

## 第一章: go并发编程和调度器

- 并发的焦点是设计结构，并行的焦点是程序的执行
  - 并发编程的本质就是要设计程序结构（不同模块可以在多核CPU中并行执行）
  - 并发的目标之一就是能利用并行（多核）的能力。但是并行的目标并不是并发，而是为了快！

- 使用了并发并不一定更快
  - 虽然 goroutine 很小，但是创建还是需要时间的，当数量过多就会产生负收益
  - 按照经验 CPU 密集型 groutine 的数量和 CPU 逻辑核数相等，I/O 密集型可以是逻辑和数的 数倍或几十倍，主要还是

- GO 运行时 goroutine 调度器
  - GPM 模型
  - G（Groutine）： 用户编写的函数或任务，轻量级协程
  - P（Processer）：逻辑处理器，负责调度绑定的G，并管理本地运行队列
  - M（Machine）： 操作系统线程，真正执行G的载体，与P绑定

### 非阻塞I/O、I/O多路复用与异步IO总结

#### 1. 核心概念与区别

| 模式                     | 核心特点                                                                 | 关键差异点                                                                 |
|--------------------------|--------------------------------------------------------------------------|----------------------------------------------------------------------------|
| **阻塞I/O**              | 线程发起I/O后一直等待，期间无法执行其他任务。                             | 实现简单，但线程利用率极低，不适合高并发。                                   |
| **非阻塞I/O（单独使用）** | 线程发起I/O后，内核立即返回“未就绪”，需通过轮询反复检查状态。             | 轮询期间线程可穿插其他任务，但无效轮询会浪费CPU，效率较低。                   |
| **非阻塞I/O + 多路复用** | 线程将I/O事件注册到“信号塔”（如epoll、kqueue），空闲时处理其他任务；就绪时“信号塔”通知线程，线程需主动完成I/O。 | 通知内容为“数据就绪”，**实际I/O操作（读/写）需线程自己执行**。               |
| **异步IO**               | 线程发起异步请求后即可离开，内核全程处理I/O（包括数据拷贝），完成后通知线程。 | 通知内容为“操作完成”，**实际I/O操作由内核完成**，线程直接使用结果。           |

#### 2. 适用场景对比

- **阻塞I/O**：  
  适合简单场景（如单任务脚本、低并发工具），开发成本低，但无法应对高并发。

- **非阻塞I/O + 多路复用**：  
  适合跨平台、高频小I/O场景（如Web服务器、Redis、Nginx），支持高并发，可控性强，是主流高并发方案。

- **异步IO**：  
  适合大I/O任务（如大文件读写）、追求开发便捷性，且运行在支持良好的OS（如Windows IOCP、Linux io_uring）上。

#### 3. 核心结论

- **本质区别**：  
  - 非阻塞I/O + 多路复用通知“数据就绪”，需线程手动完成I/O；（快递到快递站了，喊你自己去拿）
  - 异步IO通知“操作完成”，内核已处理好I/O。（快递已经送到你门口了，开门直接拿）

- **选择原则**：  
  优先考虑场景而非“方便性”：跨平台、高并发小I/O选多路复用；大I/O、OS支持良好选异步IO。

- **工程实践**：  
  高性能系统（如服务器）多采用“非阻塞I/O + 多路复用”，因其通用性和可控性；异步IO是特定场景下的优化选择。
